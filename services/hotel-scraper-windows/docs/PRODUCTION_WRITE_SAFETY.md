# Production write safety

Cloud SQL is the source of truth. The worker runs a catalog-only schema guard
before it enables production writes. The same guard covers dashboard ZIP queue
and retry actions. A mismatch in columns, types, generated geography
expressions, constraints, or required indexes leaves read-only dashboard views
available while blocking every mutation.

## Record contract

- `sources` remains `places` or `osm`, matching the existing production data.
  `raw.scraped_via` records the collection mechanism, such as
  `chrome_google_maps`.
- `hotels.geog` and `zips.geog` are generated by Cloud SQL from valid
  longitude/latitude. The worker never writes either geography field.
- Every production write carries `raw.run_id` and `raw.scraped_at`.
- `raw.google_cid` and the canonical `google_maps_uri` provide a second
  application-level identity lookup. It is not a database-enforced uniqueness
  guarantee until an approved production CID index/column migration is made.

## Inspect a run

The local durable journal is stored at:

`%LOCALAPPDATA%\HusshOne-Hotel-Scraper\scrape_run_journal.sqlite3`

Validated batches awaiting Cloud SQL are stored separately at:

`%LOCALAPPDATA%\HusshOne-Hotel-Scraper\scrape_outbox.sqlite3`

The worker flushes that outbox before it scrapes another ZIP. A crash after a
Cloud SQL commit but before local acknowledgement replays safely through the
dedup key, `place_id`, and CID lookup; it cannot create a second hotel row.
Delivered and quarantined transport batches are retained for 14 days by
default (`OUTBOX_RETENTION_DAYS`); pending batches are never pruned.

Use these read-only endpoints while the app is running:

- `GET /api/reports/writes-today`
- `GET /api/reports/runs/{run_id}`
- `GET /api/schema/compatibility`
- `GET /api/recovery`
- `GET /api/review/summary` and `GET /api/review/hotels`
- `GET /api/review/runs` and `GET /api/review/runs/{run_id}`

The dashboard's **Data Review** tab presents the same evidence without any
Cloud SQL mutation. It separates legacy/untraced rows from records carrying
this worker's `raw.scraped_via` and run ID, lets an operator filter by run and
scrape date, and reconciles each journaled before/after snapshot against the
current directory row.

The run report contains immutable pre-image and post-image snapshots for every
touched hotel and enough identity evidence to investigate a CID conflict.

## Abrupt shutdown and recovery

The browser worker shares the VM's atomic ZIP queue protocol: transactionally
select the next ZIP with `FOR UPDATE SKIP LOCKED`, mark it `in_progress`, and
commit before opening Maps. A unique `husshone-browser:` marker in `last_error`
identifies browser ownership while work is active; it is cleared on completion.
Thirty-second heartbeats refresh `updated_at`, keeping active work inside the
VM's thirty-minute stale-claim window. The browser only requeues expired browser
markers, never another VM's unmarked claim. Clean shutdown releases only owned
claims. Every result/status transaction locks the ZIP and verifies ownership.

The outbox retains its claim token. Recovery waits while another worker owns
the ZIP, then atomically reclaims available work before replay. An older
observation does not replace hotel data whose `last_seen` is newer. Hotel counts
use stored rows attributed to `query_zip`, matching VM report semantics. These
controls coordinate ZIP work; Google CID remains an application identity lookup,
not a database uniqueness constraint.

`GET /api/recovery` opens the local journal and outbox strictly read-only
(`mode=ro` plus SQLite `query_only`). It reports interrupted runs, pending
batches, malformed local payloads, and an explicit `safe_to_resume` decision.
It never acknowledges, repairs, deletes, or replays anything itself.

On a normal crash recovery, valid pending batches are replayed before the
worker can scrape a new ZIP. They are revalidated and written idempotently, so
a crash after a Cloud SQL commit but before the local acknowledgement cannot
create duplicate hotel rows. A corrupt or unreadable local journal/outbox is a
fail-closed condition: worker startup holds Cloud SQL writes for operator
review rather than silently starting a fresh audit trail.

An unfinished journal run is deliberately retained as immutable evidence. It
is shown in the dashboard for review and is never automatically marked
complete.

At startup and around each committed result batch, the worker records a
read-only hotel-count / maximum-ID watermark in the local run journal. If a
later observation is lower than a retained Cloud SQL watermark, it pauses and
refuses further writes as a suspected external deletion or unexpected restore.
It does not try to fill, delete, or "repair" production data. Stop the worker,
inspect the run evidence and Cloud SQL backup/operations history, then make a
fresh reviewed start only after the discrepancy is understood.

## No-delete application boundary

The scraper has no delete operation. In addition to the production schema
guard, every PostgreSQL connection created by this application rejects
destructive SQL (`DELETE`, `TRUNCATE`, DDL, grants, and revokes) before it is
sent to Cloud SQL. Dashboard/report request transactions are also explicitly
`READ ONLY` in PostgreSQL. These guards are defense in depth; the reviewed
least-privilege Cloud SQL role below remains the enforcement boundary that
also protects against a compromised or changed application process.

## Ongoing data-quality audit

The worker runs a bounded, read-only audit once per day by default. It checks
duplicate `raw.google_cid` values, invalid/out-of-US coordinates, malformed
rows, missing Maps trace fields, and coordinates too far from the row's query
ZIP. Shape inspection is keyset-paged; its next cursor is recorded in the
local journal and every partial result is explicitly flagged for follow-up.

You can run or inspect a page manually without changing Cloud SQL:

`GET /api/audits/data-quality?shape_scan_limit=10000&shape_cursor_after_id=...`

Set `DATA_QUALITY_AUDIT_INTERVAL_SEC=0` only when a separate approved scheduler
will run the audit instead.

## Refresh policy

`REFRESH_AFTER_DAYS` defaults to 30 days, matching the VM. Set it to 0 to leave
completed ZIPs alone. Once the
explicit pending queue is empty, the worker selects never-scraped/oldest ZIPs
first and uses `hotels_found` as a density tiebreaker. `DAILY_MAPS_CALL_CAP`
spreads the refresh workload across days.

## Reverting a run

1. Stop the worker and retain a copy of the local journal.
2. Retrieve and inspect the run report. Do not revert a row touched by a later
   run; its current `raw.run_id` will differ.
3. Run any production correction inside a reviewed transaction, beginning with
   read-only selection. Replace the placeholders through parameter binding in
   your database client—do not interpolate values into SQL text.

For rows inserted by a run, review first:

```sql
SELECT id, dedup_key, name, raw->>'run_id' AS run_id
FROM hotels
WHERE id = ANY(:inserted_hotel_ids)
  AND raw->>'run_id' = :run_id
ORDER BY id;
```

After review, the corresponding revert is deliberately narrow:

```sql
DELETE FROM hotels
WHERE id = ANY(:approved_inserted_hotel_ids)
  AND raw->>'run_id' = :run_id;
```

For a touched row, restore the specific pre-image recorded in the journal with
an `UPDATE ... WHERE id = :id AND raw->>'run_id' = :run_id` predicate. Include
only fields this scraper owns (`sources`, `rating`, `phone`, `website`, `raw`,
and `last_seen`) and have an operator review the generated parameters first.
Never issue a broad delete based solely on a date or source tag.

## CID migration decision

The current Cloud SQL schema contains no CID column or CID uniqueness index.
To make CID a database-enforced second identity key, use an approved production
migration (for example a nullable `google_cid text` plus a partial unique
index). Do not repurpose `place_id`, which has established production meaning.

## Least-privilege database role

Do not use an INSERT/UPDATE-only role for this worker: it reads `zips` to
claim, refresh, and canary-check locations; reads `hotels` to deduplicate; and
uses `INSERT ... RETURNING` (which also requires SELECT on returned columns).
The approved role should have only the following application privileges:

- `SELECT`, `INSERT`, and `UPDATE` on the required `hotels` and `zips`
  columns/tables;
- `SELECT` on any report tables exposed to this process, if those reports are
  retained;
- `USAGE` (and normally `SELECT`) on the `hotels.id` sequence for inserts;
- no `DELETE`, DDL, ownership, migration, or broad schema privileges.

Create and grant that role through a reviewed production change, then set
`DB_USER` for the worker to that dedicated account. Do not apply the role
change from the scraper process.

## Business website enrichment

With `WEBSITE_ENRICHMENT_ENABLED=true`, replaying a validated Maps batch queues
each available business website into `website_jobs.sqlite3` before the remote
Maps commit. Jobs carry the same non-secret database fingerprint as the outbox.
The worker interleaves one website job with each discovery-loop iteration and
continues draining jobs when Maps is capped or idle. Hotel Details also has an
explicit **Collect website** action for existing hotels; it only queues local
work and requires a running worker to collect and apply evidence.

Collection checks robots.txt, respects delays, follows at most three redirects,
and reads at most four relevant same-host HTML pages by default. Connections
are pinned to validated public IPs, TLS retains hostname verification, private
and metadata IPs are blocked, and no credentials/cookies/proxy settings are
inherited by HTTP requests. A child-process supervisor enforces a 150-second
deadline, including DNS hangs. Transient failures retry with backoff, up to
three attempts. Fetched evidence is persisted before any remote update, so a
database outage or crash after commit can safely replay the same evidence.

Business JSON-LD must match the Maps name and corroborate phone, ZIP or nearby
coordinates. Ambiguous sites become `needs_review`; restrictions and uncertain
cross-host redirects are not bypassed. This first version does not render
JavaScript-only websites or infer facts from free-form page text. Relevant page
excerpts remain evidence, not structured claims about amenities or policies.

The only remote change is `hotels.raw.website_enrichment`, containing source
URLs, timestamps, page hashes, status and proposed structured fields. Existing
columns, Maps trace, photos and `last_seen` are preserved. Older results and
failures cannot replace previously successful newer evidence. A changed URL or
missing/ambiguous hotel identity skips the remote update. No Cloud SQL DDL or
deletes are introduced. Review evidence in the hotel detail modal; no automatic
approval or overwrite of canonical business fields is implemented.

## Windows continuity (deployment)

Tests set an isolated temporary `LOCALAPPDATA` before importing the application.
SQLite development outboxes and journals are also separated by database target.
Every new batch records a non-secret database fingerprint; startup and replay
reject missing or mismatched fingerprints before any ZIP claim or remote write.
Legacy pending batches stay intact and hold the worker for operator review.
The worker fails closed if its durable files cannot open; it never silently
switches to a shared temporary recovery folder. Production connections are
explicitly forbidden while the test-mode marker is set.

An authorized cleanup may record an `operator_inventory_checkpoint` with its
database fingerprint, removed IDs and backup path in the local run journal.
This establishes a reviewed inventory baseline without erasing old audit
history or lowering any newer run watermark. This is not an automatic cleanup
feature: the running app's destructive-SQL firewall remains enabled.

`run_as_background_vm.ps1` launches the worker below normal priority and keeps
runtime logs under `%LOCALAPPDATA%\HusshOne-Hotel-Scraper\logs`. To prepare a
per-user login task with restart-on-crash behavior, review and explicitly run:

```powershell
.\install_autostart_task.ps1
```

The task runs only after sign-in. The process also requests a Windows wake lock
while the worker is active, but no local process can survive a machine shutdown
or power loss. Choose an always-on host if unattended overnight operation is a
requirement.
